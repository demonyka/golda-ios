# Архитектура iOS-версии

Поведение приложения описано в `SPEC.md` и не дублируется здесь. Этот документ — про то, как оно устроено на iOS и чем отличается от Android. Решения и их статус — в `DECISIONS.md`.

## Структура репозитория

```
ios/
  project.yml              XcodeGen: цели, capabilities, схемы
  Golda/                   приложение (SwiftUI)
    App/                   точка входа, сцена, deep links, приём приглашений CloudKit
    UI/                    Home, Accounts, Goals, Insights, Entry, Profiles, Settings, Onboarding, Components
    Theme/                 токены цветов, шрифты, отступы
    Platform/              запись голоса, уведомления, haptics
    Resources/             Assets.xcassets, Localizable.xcstrings, InfoPlist.xcstrings
  GoldaWidgets/            виджеты «Можно сегодня» и «Записать голосом», Control Center control
  Packages/
    GoldaCore/             домен; импортирует только Foundation
    GoldaData/             GRDB, репозитории, бэкап, клиенты курсов (ЦБ и добор), Keychain, голосовая очередь и провайдеры
    GoldaSync/             CloudKit (CKSyncEngine), шаринг
  Tests/                   UI-сценарии (XCUITest); юнит-тесты лежат в пакетах
app/ …                     Android, эталон; удаляется на этапе 7
```

Зависимости в одну сторону: `Golda` → `GoldaSync` → `GoldaData` → `GoldaCore`. Приложение собирает снимок состояния (`AppData`) **активного профиля** из репозитория и отдаёт его экранам, как на Android; логика считается в `GoldaCore`, на экранах её нет.

## Соответствие Android → iOS

| Android | iOS |
|---|---|
| Room | GRDB (SQLite), миграции `DatabaseMigrator` |
| DataStore `Settings` | настройки профиля — таблица `profile`; настройки устройства — UserDefaults (Codable) |
| Android Keystore AES-GCM | Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` |
| WorkManager | `UNUserNotificationCenter` + `BGAppRefreshTask` |
| `MediaRecorder` (Opus/AAC) | `AVAudioRecorder`, линейный PCM → WAV 16 кГц mono |
| `HttpURLConnection` + `org.json` | `URLSession` + `Codable` |
| `kotlinx.serialization` | `Codable` |
| `java.time` | `LocalDate`, `YearMonth` в `GoldaCore` (на epoch day), зона передаётся явно |
| `tr("ru", "en")`, `I18n.russian` | String Catalog; домен отдаёт структуры, текст собирает UI |
| `LocaleManager`, переключатель языка | системный язык приложения (Настройки iOS → Golda → Язык) |
| Compose, M3 Expressive | SwiftUI, HIG (см. `DESIGN.md`) |
| Плитка Quick Settings | Control Center control, Action Button |
| Виджет 1×1 | WidgetKit; на iOS ещё «Можно сегодня» с данными через App Group |
| App shortcut | App Shortcuts (App Intents), quick action |
| `POST_NOTIFICATIONS`, `RECORD_AUDIO` | запрос разрешений в момент первой нужды, строки в `InfoPlist.xcstrings` |
| `Demo` по intent-extra | аргумент запуска в debug-сборке |

На Android профилей нет: один человек, один набор данных. Профили — новая сущность iOS-версии (D21).

## Домен (`GoldaCore`)

Переносится из `app/src/main/java/sh/aminov/golda/domain/` по одному файлу вместе с тестами. Домен профилей не знает: его функции получают счета, операции, платежи, цели и `Settings` одного профиля, как получали у Android. `Settings` остаётся составным значением (профильная часть + часть устройства), его собирает слой данных для активного профиля. Тесты Android переносятся без смены ожиданий.

Места, где буквальный перевод даёт другой результат:

- **Округление.** Kotlin `roundToLong()` округляет half-up; Swift `.rounded()` — от нуля. Вся арифметика денег идёт через `Money.roundHalfUp(_ x: Double) -> Int64` (`floor(x + 0.5)`).
- **Формат сумм.** `Fmt` всегда пишет в русском стиле: узкий неразрывный пробел U+202F между тысячами, запятая, «−» (U+2212) для минуса, «4 210,50 ₽», целые суммы без «,00». Так же и при английском интерфейсе (D13). `NumberFormatter` не используется: суммы собираются из целых минорных единиц, а приближённые значения — через `String(format: "%.Nf")`, который раскладывает двоичное значение точно и округляет точные ничьи к чётному, как `DecimalFormat` JDK 8+. Отрицательное число, округлившееся до нуля, сохраняет минус («−0»), как в Java.
- **Число знаков валюты.** Таблица ISO 4217 в коде (0 знаков: JPY, KRW, VND, CLP, ISK и др.; 3: KWD, BHD…; остальным 2), сверенная тестом с `java.util.Currency` для всех валют ЦБ. `NumberFormatter` Apple не годится в эталон: для IDR, RSD и COP он отдаёт 0 знаков (наличные), а ISO и JVM — 2.
- **Разбор суммы.** `parseMinor` принимает «15», «15,5», «1 500.25» (в том числе неразрывные пробелы), отрицательные и пустые даёт `nil`; округление half-up через `Decimal`. Больше `Money.maxMinor` (10^15 минорных единиц) — тоже `nil` (D59).
- **Переполнение.** Swift падает на переполнении `Int64`, Kotlin молча заворачивает. Суммы денег в ядре, репозитории и моделях экранов идут через `Money.add`/`Money.subtract`/`moneySum`: они держатся на ±`Int64.max` (симметрично, так что смена знака тоже не падает). Слишком большая строка (бэкап Android, другой телефон) даёт неверную цифру, но не роняет каждый запуск (D59).
- **Даты.** `LocalDate` и `YearMonth` — свои значения на epoch day, зеркало `java.time`; границы дня и зона приходят параметром, как `zone` на Android. `Foundation.Date` и `Calendar` остаются на краю (БД, UI).
- **Тексты.** `Debts.advice` отдаёт `DebtAdvice`, `Goals.waitLabel` — `WaitSpan`, `Goals.facts` — `Facts` с числами, у «хочу купить» без названия `Consider.title` пуст (а `VoiceMapper` принимает локализованное `unnamedPurchase`), названия категорий UI берёт по ключу. Строки из них собирает UI через String Catalog с русскими формами множественного числа. Это единственное место, где перенос теста меняет способ проверки.
- **`VoicePrompt`.** Промпт остаётся на русском, как на Android, и не локализуется. Отличия: счета в нём нумеруются позицией в списке (D25), валюты человека перечислены с названиями и монетами (раздел «Голос»), а отступы шаблона убраны (на Android многострочная подстановка со счетами, судя по коду, мешала `trimIndent` их срезать; для модели это ничего не меняет).
- **`Settings` ядра** — только то, что читает логика: доход, день зарплаты, валюты, наценка, `lastAccountId`. Флаг онбординга, модель Gemini, напоминание, «праздник цели» и `reconciledAt` — забота приложения.
- **`CurrencyDisplay`** (строка «других валют», порядок выбора валют, переключение валют показа) живёт в ядре: это логика от настроек и курсов, и тесты настроек её проверяют. На Android она лежала в UI-слое (`AppData`, `Components.kt`).
- **Каталог валют.** Android предлагал двенадцать валют `Currencies.common`; здесь `Currencies.all` — все валюты ISO 4217 в обращении (без фондов, металлов, расчётных единиц, тестовых и изъятых кодов): сначала `Currencies.popular` (те двенадцать и фунт после евро), затем остальные по коду. `Currencies.ordered` держит в этом порядке список валют показа, поэтому место валюты не зависит от того, когда её включили, и код вне каталога (из старого бэкапа) не теряется. Названия даёт система (`Locale.localizedString(forCurrencyCode:)`, русский или английский по языку интерфейса); в длинных списках UI сортирует «остальные» по названию и ищет по названию и коду (`CurrencySections`).
- **Ошибки.** `Ledger.postings` бросает `LedgerError` там, где Kotlin бросал `NoSuchElementException`; `Fmt.parseMinor` возвращает `nil` для суммы больше `Money.maxMinor`, где Kotlin принимал до `Long.MAX_VALUE` и падал за ним; `Money.roundHalfUp(.nan)` — 0.
- **Устойчивая сортировка.** Где Kotlin полагается на стабильность `sortedBy`, используется `stableSorted`, чтобы одинаковые суммы шли в том же порядке.

## Данные (`GoldaData`)

Все id — UUID (нужно для синхронизации; Int-id Android остаются только в импорте). Деньги — `Int64` минорных единиц, курсы — `Double`. Весь учёт принадлежит профилю: у каждой строки, кроме `rate`, есть `profileId`, он же ключ зоны синхронизации и каскадного удаления.

| Таблица | Поля |
|---|---|
| `profile` | id, name, sort, incomeHourly, hourlyRate, monthlySalary, taxPercent, hoursPerWeek, payday, markup |
| `account` | id, profileId, name, currency, type, groupName?, includeInFree, sort, interestRate?, paymentDay?, paymentMinor?, graceUntil?, reconciledAt? |
| `operation` | id, profileId, sequence, type, timestamp, categoryKey?, note, voiceText?, purchaseAmountMinor?, purchaseCurrency?, isEstimate, cbrFrom?, cbrTo?, updatedAt |
| `posting` | id, profileId, operationId, accountId, amountMinor, rubMinor |
| `obligation`, `goal`, `wish` | как на Android, плюс profileId; id — UUID. У `goal` и `obligation` ещё `createdAt` — счётчик порядка создания внутри профиля (не время); отмена удаления возвращает строку на прежнее место |
| `rate` | code, rubPerUnit, date — общие курсы, не синхронизируются |
| `sync*` | миграция `v2`: журнал триггеров, очередь, штампы записей, зоны, входящие, системные поля, состояние движков — см. «Синхронизация и шаринг» |

**Курсы.** Источник — `RatesSource`; в приложении это `MergedRatesSource`: ЦБ (`CbrRatesSource`, зеркало cbr-xml-daily.ru) остаётся источником всех своих валют, а валюты, которых ЦБ не публикует (ARS, MXN, CLP…), добирает `CurrencyApiRatesSource` — бесплатный API без ключа (fawazahmed0/currency-api, CC0; jsDelivr, при сбое зеркало на Cloudflare Pages). Оба запроса идут параллельно; отказ ЦБ — отказ обновления, как раньше; отказ второго источника оставляет у этих валют прежний курс. Добранные курсы хранятся так же (рубли за единицу) с датой ответа ЦБ, чтобы «ЦБ на …» в настройках называл день ЦБ. Валюта без курса ведёт себя как всякая валюта без курса: суммы в ней стоят 0 ₽ до первого курса (`repairValuations`), основная валюта без курса показывается рублями.

Категории встроенные (на Android их нельзя изменить): задаются перечислением с ключом, иконкой и названиями в String Catalog. В операции хранится `categoryKey`.

**Настройки.** Профильная часть (`incomeHourly`, `hourlyRate`, `monthlySalary`, `taxPercent`, `hoursPerWeek`, `payday`, `markup`) лежит в `profile`; `reconciledAt` Android переехал в `account`. Часть устройства — UserDefaults: `onboarded`, активный профиль, `displayCurrencies`, `localCurrency`, `baseCurrency`, `geminiModel`, `reconcileReminder`, а `lastAccountId` и `celebratedGoalId` — по профилям. Ключи API — Keychain. `GoldaCore.Settings` собирается из обеих частей для активного профиля.

**Профили.** Первый запуск создаёт профиль «Личный». Профилей может быть сколько угодно; последний профиль удалить нельзя. Удаление профиля стирает его счета, операции, цели, вишлист и платежи (с подтверждением).

**Репозиторий.** Все изменения идут через актор `Repository`, каждое в одной транзакции и в границах профиля: проводки привязаны к профилю составными внешними ключами (D26), так что база сама откажет в проводке на чужой счёт. Запись выполняется в неструктурной `Task`, поэтому отмена вызывающего экрана не обрывает сохранение. Правка операции обновляет её проводки на месте (id проводок стабильны), чтобы синхронизация видела правку, а не удаление с созданием. `deleteOperation` возвращает `DeletedOperation`, и «Отменить» через `restoreOperation` возвращает операцию с теми же id и на то же место среди записей с одинаковым временем (для этого и нужен `sequence`, D27). `saveAccount` не трогает `reconciledAt`: его пишет только `reconcile`. `refreshRates` и `ensureSeed` переоценивают проводки со стоимостью 0 ₽ во всех профилях, каждый по своей наценке. `Repository` получает `SecretStore`: «Стереть всё» (`resetAll`) удаляет и ключи API, как `settings.clear()` на Android (D28).

Читающие модели отдают данные, не строки: `impact` (часы работы, стоимость, остаток на сегодня), `consider` (`Facts` с `waitHours`), составной `Settings(profile:device:profileId:)`.

**Бэкап.** JSON `version: 2` со всеми профилями (Codable, `ignoreUnknownKeys`, ключи отсортированы, чтобы файлы хорошо сравнивались; проводки вложены в свои операции; порядок создания целей едет отдельным полем `goalCreatedAt`; экспорт пустой базы отклоняется как `nothingToExport`; повторный экспорт после импорта совпадает побайтно). Импорт читает `version: 1` Android: Int-id → UUID, `categoryId` → `categoryKey`, всё содержимое попадает в новый профиль «Личный», доход, день зарплаты и наценка уходят в него, настройки устройства — в UserDefaults. Файл читается целиком до изменения данных; битый файл ничего не меняет. Ключи API в бэкап не входят.

**Файлы.** Голосовая очередь — `Application Support/voice/<epochMillis>.wav` с `isExcludedFromBackup`.

## Синхронизация и шаринг (`GoldaSync`)

Цель: общий бюджет с разными людьми — с женой, с другом, с коллегами — без пересечения данных. У участников разные Apple ID. Сервера нет, только iCloud. Единица шаринга — **профиль** (D7, D21).

**Модель CloudKit.**
- **Один профиль — одна зона** в private БД владельца (`profile-<uuid>`), **один `CKShare` на зону** (`CKShare(recordZoneID:)`). Приглашённый видит зону в своей shared БД.
- В зоне записи `Profile` (корень), `Account`, `Operation`, `Obligation`, `Goal`, `Wish`. Ссылки между ними остаются внутри зоны, записи повторяют локальные таблицы, кроме проводок.
- Операция и её проводки — одна запись `Operation` (проводки списком в поле `postings`): приёмник никогда не видит половину перевода, а конфликт решается для операции целиком (D58).

**Движок.** Два `CKSyncEngine`: на private и на shared БД (`CloudKitSyncTransport`, проверено спайком 5a, S1). Состояние движков и очередь исходящих изменений хранятся в файле книг (GRDB). Транспорт стоит за протоколом `SyncTransport`; тесты работают с заглушкой `InMemorySyncTransport` над `InMemoryCloud` (зоны, шаринг, теги изменений, отказ «подождите N с»). `SyncService` (`GoldaSync`) запускает транспорт, когда есть iCloud, после каждого локального изменения даёт новым своим профилям зоны, сообщает серверу об удалённых и покинутых профилях и передаёт очередь. В приложении им владеет `AppSync`: запуск при старте и при каждом возвращении (человек мог войти в iCloud), состояние для экранов, участники, приглашение, приём приглашений. Приглашение принимается в `windowScene(_:userDidAcceptCloudKitShareWith:)` и при холодном запуске (Info.plist: `CKSharingSupported`), в любой сборке; пришедший профиль открывается.

**Что общее, что личное.** Профиль целиком общий для его участников: счета, операции, цели, вишлист, платежи, доход, день зарплаты, наценка. «Можно сегодня» у всех участников профиля считается одинаково по общим данным. На устройстве остаются язык, валюты показа, местная и основная валюта, ключи API, модель Gemini, активный профиль (D16).

**Правила.**
- **Конфликты:** последний записавший побеждает по `updatedAt` на уровне записи. Балансы и рублёвая стоимость сходятся, потому что это суммы проводок; средняя себестоимость при одновременной записи с двух телефонов на один валютный счёт может чуть отличаться от последовательной — стоимость фиксируется на стороне автора.
- **Переводы** только внутри профиля (D22): обе проводки в одной зоне. Деньги между профилями — расход в одном и доход в другом.
- **Права.** Приглашённый читает и пишет; приглашение — только для приглашённых, «по ссылке» владелец выбирает в листе приглашения (D58, закрывает O3). «Только просмотр» не предлагается; если сервер всё же отказал в правке (`permissionFailure`), телефон берёт версию сервера (`SyncStore.refused`).
- **Приглашение:** «Пригласить…» на экране профиля открывает системный лист (`ShareLink` с `CKShareTransferRepresentation`): AirDrop, Сообщения, Почта, «Скопировать ссылку». `CKShare(recordZoneID:)` создаётся, только когда выбран способ. На экране профиля — участники, «Закрыть доступ» у владельца, «Выйти из профиля» у участника; без iCloud «Пригласить…» выключено и сказано почему.
- **Выход участника или прекращение доступа:** движок сообщает об удалении зоны; приложение удаляет локально профиль и все его данные, уведомления пересчитываются без него, а активным становится другой профиль. Выход с этого телефона идёт тем же путём, что удаление профиля: книги удаляются сразу, зона помечается к выходу, сервер слышит об этом сейчас или когда появится сеть.
- **Удаление профиля владельцем** удаляет зону: у участников профиль пропадает. Участник «удаляет» профиль, выходя из доступа.
- **Последний профиль.** Если синхронизация забрала последний профиль, на его месте в той же транзакции появляется пустой «Личный»; выход из последнего профиля делает то же.
- **Удаление и «Отменить»:** исходящее удаление уходит после окна отмены (10 с); отмена до отправки снимает его.
- **Хранилище.** Данные общих профилей лежат в iCloud владельца и расходуют его место.
- **Без iCloud:** приложение работает локально, шаринг недоступен, очередь копится; при появлении iCloud все свои профили, которых синхронизация ещё не знает, выгружаются целиком в свои зоны.
- **Смена iCloud-аккаунта:** общие профили старого аккаунта уходят с телефона (у владельца они целы), свои книги остаются и выгружаются в зоны нового; состояние движков и очередь сбрасываются, кроме неотправленных удалений своих записей и своих зон удалённых профилей: они уходят в новой сессии. Зона, которую потерял сервер (удалены данные iCloud, сброс шифрования), выгружается заново из книг.
- **Ждать, когда просят.** Изменение, на которое сервер ответил `retryAfterSeconds` (и полный iCloud без срока — 300 с), уходит из движка и возвращается к нему только по сроку; повторное приглашение до срока сразу говорит, сколько ждать. Ошибки iCloud приложение показывает словами (`SyncProblem` → `SyncProblemText`).
- **Курсы** не синхронизируются: каждый телефон берёт их сам.
- **Автор записи** виден как последний изменивший участник; показ в интерфейсе — после версии 1.

**Записи и очередь** (D57, D58). Имя записи — `<Тип>.<uuid>`, типы — `Profile`, `Account`, `Operation`, `Obligation`, `Goal`, `Wish`; содержимое — в `encryptedValues`, открыты только `updatedAt` и `authorDevice`. В `Operation` лежат её проводки (`postings`, JSON-список), у `Goal` и `Obligation` — `createdAt` (место в порядке создания).

Исходящее: таблицы синхронизации — в миграции `v2` файла книг. Триггеры на семи таблицах пишут каждую изменённую строку (и те, что ушли каскадом) в `syncJournal`; изменённая проводка записывается как изменение своей операции (`v3`), и `GoldaDatabase.write` до коммита превращает журнал в записи очереди `syncOutgoing` (одна на запись CloudKit: последнее желание побеждает, удаление ждёт окна отмены) со штампом времени и id установки в `syncMeta`. Так очередь меняется в одной транзакции с книгами, через что бы ни шла запись. Правка, не задевшая синхронизируемых столбцов (порядок профилей, `sequence` операций), никуда не уходит. Удалённый профиль не превращается в удаления строк: его зона помечается в `syncZone` к удалению (у владельца) или к выходу (у участника). Зона профиля — строка `syncZone`; профиль без строки — свой, ещё не выгруженный.

Входящее: `SyncStore.apply` решает конфликт по записи (последний записавший; ждущее локальное удаление сильнее пришедшей записи, пришедшее удаление сильнее ждущей правки), кладёт победившее в `syncInbox` и переносит в книги то, что может там стоять: всё — после профиля, операцию — после счетов её проводок, и её проводки заменяют хранимые в порядке записи. Перед входом в книги ждавшая запись сверяется снова: локальная правка, сделанная, пока она ждала, сильнее. Удаление счёта забирает операции на нём, как локальное, и отправляет их удаление. Отказ сервера в правке (`permissionFailure`) возвращает версию сервера (`refused`). Принятое в очередь не возвращается (журнал очищается без отправки). Своё место в списке профилей и порядок операций с одним временем у каждого телефона свои. `syncSystemFields` держит системные поля записей, чтобы следующее сохранение несло change tag; конфликт при отправке (`serverRecordChanged`) решается тем же правилом.

Диагностика: в Debug «Настройки → Sync» показывает состояние iCloud, зоны профилей, очередь, ждущие входящие и журнал транспорта (его можно скопировать).

Открыто: передача владения (O2).

## Голос

`Запись → очередь → провайдер → VoiceMapper → операции → «Записано» + «Отменить»`.

- **Запись** — `AVAudioRecorder`, линейный PCM 16 кГц, mono, 16 бит (WAV, около 32 КБ/с); максимум 60 с; касание короче 0,8 с и тишина (по `averagePower`) ничего не отправляют. Файл называется временем записи.
- **Звуки.** Перед записью — восходящий двузвучный сигнал и тактильный отклик, после остановки — нисходящий (`VoiceCues`; свои звуки, `Resources/Sounds/voice-start.wav` и `voice-stop.wav`, их пишет `ios/tools/voice_chimes.py`). Рекордер запускается внутри `listen(then:)`, когда сигнал отзвучал, а останавливается внутри `stop(_:)` до нисходящего, так что ни один сигнал в запись не попадает. Сессия одна на сигналы и рекордер (`VoiceAudioSession`, счётчик удержаний): `.playAndRecord`, звук из динамика, а не из разговорного, в Bluetooth-наушники при их наличии; категория записи играет и при беззвучном режиме, как сигналы Siri.
- **Профиль.** Заметка пишется в профиль, который был активен в момент записи; промпт перечисляет счета этого профиля и валюты человека (местная, показа, основная, валюты счетов); подтверждение называет профиль, если их больше одного.
- **Валюты в голосе.** Каждая валюта человека идёт в промпт с русским названием из `Locale("ru")`, разговорными словами и разменной монетой из таблицы `SpokenCurrency` (`Voice.swift`): «- GEL — грузинский лари, «лари»; тетри = 1/100». Правила промпта: общее для нескольких валют слово («песо», «доллар», «крона»…) — своя валюта, если такая у человека одна, иначе обычная; монета пишется долей основной единицы («50 тетри» → "0.50" GEL), это запись числа, не пересчёт. Страховка в коде: если модель вернула код, которого у человека нет, а из его валют то же основное слово носит ровно одна, `VoiceMapper` берёт её (MXN при ARS → ARS). Модель отдаёт только код, без слов, поэтому страховка не трогает слова популярных валют (рубль, доллар, фунт, рупия…): голое слово даёт популярный код, а другой код под этим словом назван явно («белорусских рублей» — BYN, никогда не RUB). Разные написания («риал» и «риял») — разные слова.
- **Очередь** обрабатывается последовательно (актор) при запуске, при возврате в приложение и после ввода ключа. Без сети или ключа запись ждёт; время операции — время записи. Файл, выданный рекордеру (`VoiceService.newNote`), принадлежит ему до конца его `understand(file:)`: очередь его пропускает, даже если запись остановлена давно (иначе прогон очереди, начатый во время записи, забрал бы её, а вызов рекордера нашёл бы пустоту и сказал «потеряна»); оставшаяся ждать заметка после этого — очереди.
- **Провайдер** — протокол `VoiceProvider` (`parse(audio, system, model) -> VoiceResult`). В версии 1 один: `GeminiProvider` — тот же запрос и `responseSchema`, что на Android, заголовок `x-goog-api-key`, MIME `audio/wav`, модель задаётся в настройках.
- **Согласие.** До первой отправки — экран с названием провайдера и тем, что именно уходит (правило 5.1.2(i)); отзыв — в настройках. Без согласия сеть не вызывается.
- **Ключ** — в Keychain; настройки хранят только «ключ есть».
- Модель только извлекает; `VoiceMapper` проверяет и считает.

## Вне приложения

- **Уведомления.** Все локальные и по всем профилям, в которых состоит человек: таймеры вишлиста (разовые на `decideAt`), платёж по долгу за 3 дня и в день платежа, льготный период за 7, 1 и 0 дней (напоминания о долгах — в 10:00 по местному времени того дня), сверка по воскресеньям в 19:00 (повтор, одна на все профили). План строит `GoldaCore.Reminders` (значения, без слов; слова — таблица `Reminders` приложения), `ReminderScheduler` сверяет его с ожидающими запросами `UNUserNotificationCenter` и заменяет только изменившиеся. В iOS код нельзя запустить в момент показа, поэтому план пересчитывается при запуске и возвращении в приложение, при изменении книг любого профиля или переключателя сверки и в `BGAppRefreshTask` (`com.f4studio.golda.reminders`). У каждого долга планируются сразу все напоминания двух ближайших платежей и льготного периода, каждое — отдельным запросом с днём в id (`payment.<счёт>.2026-10-22`): приложение может не запуститься до нужного дня. Весь план — не больше 60 ближайших: у iOS лимит 64 ожидающих уведомления. Нажатие переключает на нужный профиль и открывает нужное место: вишлист — покупку в «Сомневаюсь», долги — «Счета», сверка — «Счета» в режиме сверки. Разрешение спрашивается при первой нужде: «Подумаю», включение сверки, долг с датой платежа или льготного периода.
- **Точки входа в запись.** Один `StartVoiceNoteIntent` питает Control Center control (iOS 18+), Action Button, App Shortcuts (Siri, Spotlight), кнопку микрофона виджета «Можно сегодня» (`MicButton`) и виджет «Записать голосом» (маленький на экране «Домой» и круглый на экране блокировки; кнопка растянута на весь виджет, под ней остаётся ссылка `golda://voice` для касания мимо кнопки). Это `AudioRecordingIntent` и `LiveActivityIntent` с `supportedModes = [.background, .foreground(.dynamic)]`: система выполняет его в процессе приложения, не показывая его.
- **Запись без приложения** (`BackgroundVoiceNote`, `VoiceNoteLauncher`). Куда идёт запрос, решает `VoiceNoteRoute`: если идёт запись вне приложения — она останавливается (повторное нажатие, как второе касание микрофона); если приложение на экране — его микрофон, как раньше; если микрофон приложения ещё пишет, а приложение ушло с экрана (режим `audio` его не останавливает), — запрос останавливает эту запись, второй рекордер не запускается; иначе запись идёт без приложения, только когда есть всё: пройден онбординг и открыт профиль, дано согласие на голос, есть ключ Gemini, микрофон разрешён, Live Activity разрешены. Чего-то нет — `continueInForeground(alwaysConfirm: false)` поднимает приложение, и дальше всё как у касания (экран согласия, системный запрос микрофона, тост про ключ). Порядок: Live Activity «Слушаю…» с секундами и «Стоп» (без неё iOS не пишет в фоне, а запустить её с приложением вне экрана может только `LiveActivityIntent`: иначе ActivityKit отказывает с `visibility`), затем восходящий сигнал, затем микрофон. «Стоп» (`StopVoiceNoteIntent`), повторный запуск интента, касание микрофона в приложении или конец минуты: нисходящий сигнал, «Разбираю…», тот же `VoiceService`, что у микрофона, под `beginBackgroundTask`. Нажатие во время восходящего сигнала отменяет запись до включения микрофона (и у микрофона приложения). Если фоновое время кончается раньше ответа, обработчик истечения переводит Live Activity в «Открой Golda, чтобы закончить запись» (и уведомление), затем завершает задачу: незавершённая задача приводит к убийству процесса; заметка ждёт в очереди. Процесс может умереть посреди заметки, поэтому у «Слушаю…» `staleDate` — начало + 75 с, у «Разбираю…» — сейчас + 90 с, и виджет показывает устаревшее состояние как «Открой Golda, чтобы закончить запись»; при запуске и при «Стоп» без записи этого запуска `LiveVoiceActivities.endStale` сразу завершает активности, которые этот запуск не начинал. Итог — на Live Activity (`VoiceActivityContent`, слова тостов): «Шаурма 15 ₾» и строка влияния с «Отменить» (`UndoVoiceNoteIntent` с id операций, требует разблокировки) или причина, по которой нужна Golda. Голос записывает сразу с отменой, как в приложении; что приложение подтверждает экраном («хочу купить» в «Сомневаюсь») и любая причина ожидания или сбоя оставляют ещё и локальное уведомление (только если уведомления уже разрешены), касание открывает приложение. Итог виден 5 с в Dynamic Island и минуту на экране блокировки. Результат получает и микрофон приложения: если приложение уже было на экране, — через поток исходов, как заметку из очереди; если процесс запущен только ради интента, — `VoiceMicModel.keepUntilShown`, тост или форма появятся при открытии. Фоновый режим `audio` держит приложение, пока идёт запись.
- **Запрос в приложение.** quick action на иконке объявлен в Info.plist и принимается `AppDelegate`/`SceneDelegate` при холодном и тёплом запуске; ссылка `golda://voice` и интент, которому нужен экран, — тоже. Все пути кладут один запрос в `VoiceEntryRequests` (как conflated-канал Android: повтор до разбора — та же запись), а `VoiceEntryDelivery` на вкладке отдаёт его микрофону, как касание: только когда приложение активно (микрофон пишет лишь на переднем плане), открыты вкладки (запрос ждёт онбординг) и поверх нет листа (форма с введённым остаётся, запись начнётся после её закрытия); открытые поверх вкладки страницы закрываются, у них нет микрофона. Дальше всё как у касания: экран согласия, если его не было, обычные тосты без ключа; идущую запись запрос не трогает.
- **Виджет «Можно сегодня»** (`TodayWidget`: маленький и средний на экране «Домой», прямоугольный и строка на экране блокировки). Виджет не открывает базу: приложение кладёт в App Group `group.com.f4studio.golda` (UserDefaults группы, ключ `today.snapshot`) Codable-снимок `TodaySnapshot` — героя Home активного профиля: имя профиля, остаток дня в минорных единицах основной валюты, доля дня и строка других валют — текстом Home, дни до зарплаты, заполнение полосы, перерасход. Дней в снимке два: сегодня и завтра. Завтрашний считает тот же `Budget.today` на завтрашнюю дату: он зависит только от балансов и дня, так что это ровно то, что Home покажет завтра, если ничего не записать. Таймлайн (`TodayTimeline`) — запись на сейчас, запись завтрашнего дня на ближайшую полночь и запись «Открой Golda, чтобы обновить» на полночь после него: цифру прошедшего дня виджет не показывает. Пишет `TodayWidgetPublisher` модели: после каждого `AppData` (запуск, изменение книг, настроек, списка профилей), при уходе приложения в фон и в `BGAppRefreshTask` (читает книги сам: фоновый запуск может не открыть окна); WidgetKit перезагружается только при изменении снимка. При уходе в фон, если обновление не запрошено напоминаниями (нет разрешения), запрашивается обновление после полуночи. До конца онбординга снимка нет, виджет просит открыть приложение. Суммы форматирует `Fmt` из `GoldaCore` (виджет зависит от пакета), как в приложении. In-memory запуск пишет снимок в свой набор UserDefaults; `-golda.liveWidgets` в debug отдаёт его настоящему виджету.
- **Ссылки виджетов** (`AppLink`): `golda://voice` — запись, `golda://new` — форма новой операции, как «+» на панели, `golda://home` — касание мимо кнопок, вкладка Home. `AppLinkRequests` держат ссылку, пока вкладки не смогут её выполнить (запуск, онбординг); форма ждёт закрытия листа поверх вкладок, как запись, а уже открытая форма новой операции и есть то, что просили.

## Сборка, тесты, релиз

- **Проект:** XcodeGen генерирует `Golda.xcodeproj` из `project.yml`. Цели: `Golda`, `GoldaWidgets`, `GoldaUITests`. Пакеты подключены по пути.
- **Capabilities:** iCloud (CloudKit), контейнер `iCloud.com.f4studio.golda`; Push Notifications и фоновый режим `remote-notification` (для тихих пушей CloudKit); Keychain; App Group `group.com.f4studio.golda` у приложения и `GoldaWidgets` (`entitlements` целей в `project.yml`, файлы генерируются и лежат в `.gitignore`). Info.plist: `CKSharingSupported`, `NSMicrophoneUsageDescription`, URL-схема `golda`, `UIApplicationShortcutItems`, `BGTaskSchedulerPermittedIdentifiers` с фоновым режимом `fetch` (напоминания), фоновый режим `audio` и `NSSupportsLiveActivities` (запись без приложения). Ключи без `INFOPLIST_KEY_` пишутся в `info.properties` цели в `project.yml`; XcodeGen генерирует из них `Golda/Info.plist` и `GoldaWidgets/Info.plist` (в `.gitignore`), остальное Xcode добавляет из настроек сборки. Нужен privacy manifest (UserDefaults, файловые метки).
- **Тесты:** юнит — Swift Testing в пакетах (`swift test` без симулятора); сценарии — XCUITest на симуляторе iPhone 17 (iOS 26.2), приложение поднимается с in-memory БД и отдельными UserDefaults.
- **CI:** `.github/workflows/ios.yml` на раннере `macos-26` (Xcode 26.x по умолчанию): тесты ядра, сборка остальных пакетов, генерация проекта и сборка приложения без подписи.
- **Версии:** iOS стартует с `0.1.0`; `1.0.0` — первый релиз в App Store; номер сборки растёт автоматически.
